1. Resumen

El Banco XYZ migra su plataforma legacy (COBOL + scripts Shell sobre mainframe) hacia una arquitectura de microservicios en la nube. La solución implementa la migración de los procesos batch con Spring Batch, el patrón Backend for Frontend (BFF) para tres canales y microservicios resilientes y seguros con Spring Cloud (Config Server, Eureka, API Gateway, OAuth 2.0, Resilience4j y Apache Kafka), desplegados con Docker y preparados para AWS.

2. Objetivos y alcance

  • Reescribir los procesos batch legacy con Spring Batch (3 jobs sobre fin_legacy_data), con copia legacy + reescritura.
  • Desacoplar los frontends mediante BFFs independientes por canal (Web, Móvil, Cajeros).
  • Dividir el monolito en 3 microservicios (clientes, cuentas, pagos) resilientes y seguros.
  • Desplegar en la nube (AWS) con Docker, escalabilidad horizontal y mensajería asíncrona.

3. Requerimientos clave del negocio y decisiones de arquitectura

3.1 Requerimientos clave

  1. Escalabilidad — el sistema debe crecer horizontalmente ante mayor demanda.
  2. Resiliencia — un fallo en un módulo no debe tumbar todo el sistema.
  3. Seguridad — protección de datos y servicios en un entorno distribuido.
DecisiónJustificación
Microservicios (clientes, cuentas, pagos)Aislamiento de fallos, despliegue independiente y escalado por servicio.
Spring Batch + copia legacyReescribe los jobs legacy con retry/skip, normalización de fechas, paralelismo y re-ejecución, manteniendo equivalencia de resultados.

8. Integración entre componentes

  • Síncrona: BFF → API Gateway (HTTP + JWT) → microservicios. El Gateway resuelve los nombres lógicos (lb://ms-*) mediante Eureka.
  • Asíncrona (Kafka): eventos clientes, retiros, transacciones, autenticaciones. ms-cuentas actualiza saldos consumiendo transacciones (consistencia eventual).
  • Seguridad: auth-server emite JWT; microservicios y BFFs son resource servers que validan el token vía JWK Set.
  • Configuración: los microservicios importan config desde config-server.

9. Seguridad

  • Autenticación: OAuth 2.0 (client credentials) por canal (bff-web-client, bff-mobile-client, bff-atm-client).
  • Autorización: roles ROLE_WEB, ROLE_MOBILE, ROLE_ATM. Reglas finas (retiro → ROLE_ATM; alta de cliente → ROLE_WEB).
  • Transporte: HTTPS en los BFF (certificado autofirmado en desarrollo; ACM en AWS).
  • Control de acceso: 401 sin token, 403 sin permiso.

10. Resiliencia y mensajería

Resilience4j (en los BFFs, como consumidores): Circuit Breaker (backendCore), Retry y Fallback. Ante la caída de ms-cuentas, el BFF responde con un fallback controlado sin romper el canal.

Kafka: productores en auth-server, ms-clientes, ms-cuentas y ms-pagos; consumidores en notificaciones-service y ms-cuentas.

11. Despliegue (Docker y nube)

Un único docker-compose.yml orquesta MySQL, Kafka/Zookeeper, Kafka UI, Config Server, Eureka, Gateway, Auth Server, los 3 microservicios, el batch, los 3 BFF y notificaciones (13 servicios). Cada microservicio tiene su Dockerfile multi-etapa (Maven 3.9 + JRE 21).

flowchart TB COMPOSE[docker-compose.yml] --> MYSQL[mysql:8.4] COMPOSE --> ZK[zookeeper] COMPOSE --> KF[kafka] COMPOSE --> KUI[kafka-ui] COMPOSE --> CFG[config-server] COMPOSE --> EUR[eureka-server] COMPOSE --> GW[api-gateway] COMPOSE --> AUTH[auth-server] COMPOSE --> MS1[ms-clientes] COMPOSE --> MS2[ms-cuentas] COMPOSE --> MS3[ms-pagos] COMPOSE --> BATCH[banco-batch] COMPOSE --> B1[bff-web] COMPOSE --> B2[bff-mobile] COMPOSE --> B3[bff-atm] COMPOSE --> NOTI[notificaciones-service]

Para AWS: ECR + ECS (Fargate) + RDS MySQL + ALB + ACM + Secrets Manager (+ MSK para Kafka). Ver despliegue.md.

12. Resultados

  • Los 3 procesos batch se ejecutan (estado: COMPLETED) con normalización de los 4 formatos de fecha y retry/skip; los inválidos quedan registrados como anomalías.
  • Los 3 BFFs autentican por canal y sirven respuestas adaptadas (Web detallado 4,5 KB / Móvil ligero 3,15 KB / ATM saldo 431 B).
  • Los 3 microservicios se registran en Eureka y son accesibles vía Gateway.
  • Verificación de 401/403 y fallback de Resilience4j.
  • Eventos reproducidos productor → consumidor en Kafka (UI + consola).

14. Desafíos y soluciones

DesafíoSolución
Datos legacy sucios (negativos, fechas, nulos, duplicados)Validación/normalización en ItemProcessor + retry/skip + deduplicación en BD.
Fechas multi-formato descartadas por el legacyParser de 4 formatos (ParseoUtil.parseFecha).
Anti-patrón de procesadores con estadoProcesadores stateless; dedup por clave única.
Consistencia distribuidaEventos Kafka (consistencia eventual).
Fallos de servicios externosResilience4j (Circuit Breaker/Retry/Fallback).
Seguridad distribuidaOAuth 2.0 + autorización por canal.

15. Propuestas de mejora y próximos pasos

  • Observabilidad: OpenTelemetry + trazabilidad distribuida (tracing) entre microservicios y BFFs.
  • Contratos por canal versionados (evolución de DTOs de cada BFF).
  • CI/CD: GitHub Actions (build → tests → ECR → ECS).
  • Seguridad: rotación de claves JWT, mTLS, secretos en Secrets Manager.
  • Patrón Saga (coreografía) para transacciones distribuidas con compensación.
  • BD por servicio (esquemas/BBDD independientes por microservicio).
  • Kafka en AWS (MSK o EC2) con los microservicios apuntando al broker remoto.
